1. NUEVO ENFOQUE DEL PROYECTO
==================================================

Ahora Local seguirá siendo una aplicación móvil orientada a centralizar información local de una comuna, pero YA NO tendrá funcionalidades de delivery ni de realización de pedidos.

El proyecto se desarrollará utilizando:

- Flutter para el frontend móvil.
- Laravel para el backend.
- PostgreSQL como base de datos.
- La aplicación final estará enfocada únicamente en Android.
- No desarrollaré una versión web para usuarios finales.
- El backend expondrá una API para ser consumida por Flutter.

Por lo tanto, elimina del alcance todo lo relacionado con:

- pedidos
- delivery
- productos para compra
- detalle de pedidos
- estados de pedidos
- direcciones de entrega
- métodos de pago asociados a pedidos
- carrito de compra
- comercio electrónico
- cualquier flujo cuyo propósito sea comprar o solicitar productos a domicilio

No quiero que intentes conservar Delivery "por si acaso". El nuevo proyecto NO tendrá Delivery.

2. NUEVO MÓDULO DE INFORMACIÓN LOCAL
==================================================

El primer gran componente del sistema será un módulo de información local.

La aplicación permitirá consultar información de distintos lugares o servicios de la comuna.

Por ejemplo:

- farmacias
- restaurantes
- comercios
- cajeros automáticos
- otros lugares o servicios relevantes

La aplicación NO permitirá comprar productos ni realizar pedidos.

La información que interesa almacenar/mostrar es principalmente:

- nombre
- tipo o categoría
- dirección
- ubicación geográfica
- teléfono o medio de contacto
- horarios de atención
- días de atención
- otra información básica útil del lugar

La aplicación debe poder mostrar estos lugares en un mapa y permitir filtrar la información según su categoría.

Necesito que revises los requerimientos existentes del módulo Mapa y determines cuáles siguen siendo válidos, cuáles deben modificarse y cuáles deben eliminarse.

3. NUEVO MÓDULO: FORO COMUNITARIO
==================================================

El antiguo "Tablón de Anuncios" cambiará conceptualmente a un "Foro Comunitario".

Esta modificación es importante.

NO quiero modelarlo como un simple sistema de anuncios.

La idea es que Ahora Local tenga 4 foros comunitarios principales, cada uno asociado a un tema o espacio de conversación muy común dentro de una ciudad/comuna.

Por ahora no quiero fijar obligatoriamente los nombres definitivos de los cuatro foros si eso requiere una decisión posterior, pero quiero que el sistema esté diseñado para soportar exactamente 4 foros principales y que estos puedan configurarse mediante datos, no mediante cuatro tablas separadas.

Cada foro permitirá que los usuarios publiquen mensajes.

La idea general es:

FORO
 └── MENSAJES
       └── publicados por USUARIOS

Los mensajes normales deben aparecer ordenados cronológicamente o utilizando una lógica de publicación razonable.

4. CONCEPTO DE MENSAJE DESTACADO
==================================================

Esta es una de las partes más importantes del nuevo proyecto.

El modelo de negocio de Ahora Local estará basado principalmente en los "mensajes destacados".

Un mensaje destacado NO debe entenderse como un anuncio separado de los mensajes normales.

Es un mensaje normal del foro al que se le otorga una condición especial de visibilidad.

Conceptualmente:

Usuario publica mensaje
        ↓
Mensaje normal
        ↓
Mensaje puede convertirse en destacado
        ↓
Permanece visible durante más tiempo
        ↓
Tiene prioridad sobre mensajes normales
        ↓
Aparece siempre arriba mientras esté vigente

La idea visual/comportamental es parecida al funcionamiento del chat global de Clash of Clans, donde un mensaje con prioridad puede permanecer arriba y tener mayor visibilidad.

El mensaje destacado debe:

- aparecer antes que los mensajes normales;
- permanecer arriba mientras esté vigente;
- tener una fecha de inicio;
- tener una fecha de término;
- dejar automáticamente de ser destacado cuando termine su vigencia;
- seguir existiendo como mensaje normal después de perder el estado destacado, salvo que se determine otra regla;
- permitir implementar una lógica de monetización.

El sistema debe dejar preparada la arquitectura para que en el futuro un usuario, comercio o administrador pueda pagar para destacar un mensaje.

IMPORTANTE:
No quiero que inventes una pasarela de pago si todavía no está definida.

En esta etapa quiero que el modelo de datos y los requerimientos permitan representar correctamente el concepto de "mensaje destacado", pero el mecanismo exacto de pago puede quedar como una decisión futura.

También quiero contemplar que un destacado pueda ser activado mediante validación administrativa en caso de que todavía no exista integración de pagos.

5. USUARIOS
==================================================

Quiero simplificar considerablemente el sistema de usuarios.

La cuenta de usuario debe ser similar conceptualmente a plataformas sencillas como Pokémon Showdown.

El usuario no necesita un perfil social complejo.

La cuenta debe estar basada principalmente en:

- nombre de usuario
- contraseña
- correo electrónico O número de teléfono asociado

El correo o teléfono se utilizará como medio de asociación/recuperación/autenticación según corresponda.

No quiero que diseñes una red social ni perfiles complejos.

La entidad Usuario debe mantenerse simple.

La contraseña obviamente debe almacenarse de forma segura mediante hash y nunca en texto plano.

También analiza si realmente necesitamos mantener la tabla ROLES y USUARIO_ROL del modelo antiguo. Si se justifica conservar roles para administración del sistema, propón una solución simple. No mantengas complejidad únicamente porque existía en el modelo anterior.
